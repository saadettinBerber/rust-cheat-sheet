02 Değişkenler

let ile oluşturulan bağlama varsayılan olarak değiştirilemez. Değişiklik için mut ekle.

07 Girdi ve dönüşüm

Girdiyi metin olarak oku; sayıya dönüştür.

Bir satır oku, sayıya dönüştür

use std::io;
let mut text = String::new();
io::stdin().read_line(&mut text)
    .expect("Read failed");
let age: u32 = text.trim().parse()
    .expect("Enter a number");

&mut text değiştirilebilir referanstır. read_line girdiyi metne ekler; trim() kenardaki boşlukları ayıklar; parse() dönüşümü dener.

Hata olursa: expect mesajla birlikte panic üretir. Hatayı ele almak için match kullanabilirsin.

08 match ile sonuç

Result, başarıda Ok; hatada Err taşır.

Başarı ve hata kolları

let input = "24";
let number: u32 = match input.parse() {
    Ok(value) => value,
    Err(_) => 0,
};

Geçersiz girdide 0 kullanılır; _ hata değerini yok sayar.

İki sayıyı karşılaştırma

use std::cmp::Ordering;
let value = 9;
match value.cmp(&12) {
    Ordering::Less => println!("Less"),
    Ordering::Equal => println!("Equal"),
    Ordering::Greater => println!("More"),
}

09 Bloklar ve kapsam

KİŞİSEL RUST NOTLARI / 03 · OWNERSHIP 1/3

Rust / Stack ve değerler

Çağrıdan önce, çağrı sırasında, dönüşte.
Brown · 4.1 · Collections Use Boxes dahil

Örnek / L1 → L2 → L3

fn increment(value: i32) -> i32 {
    let result = value + 1; // L2
    result
}
fn main() {
    let number = 5; // L1
    let next = increment(number); // L3
    println!("{number} {next}");
}

Bellek resmini nasıl okuyacağız?

Frame
Bir fonksiyon çağrısının yerel bağlamalarını gösteren kutu. Çağrı başlar, frame eklenir; çağrı biter, kaldırılır.
Stack
Etkin çağrıların frame’leri. Burada en yeni çağrıyı üstte çiziyoruz; ilk o döner.
Heap
Bir fonksiyon frame’ine bağlı olmadan yaşayabilen ayrılan alanlar. Sonraki sayfada Box ile göreceğiz.

L1–L3, kodda işaretlenen satır tamamlandıktan sonraki anı gösterir. number ve value ayrı bağlamalardır.

Bir fonksiyon çağrısının üç anı

Akış: soldan sağa →

Copy: bağımsız iki değer

let a = 5;
let mut b = a;
b += 3;
println!("{a} {b}"); // 5 8

i32 tipi Copy olduğu için b ayrı bir değer alır. b değişince a değişmez.

Önemli ayrım

Copy, bir tip özelliğidir; “stack’te olan her şey kopyalanır” kuralı yoktur. String ve Box<T> değerle aktarılırken taşınır.

Bu modeldeki kutular gerçek bellek adresleri değildir. Derleyici değerleri register’da tutabilir veya işlemleri optimize edebilir.

KİŞİSEL RUST NOTLARI / 04 · OWNERSHIP 2/3

Rust / Box, move ve drop

Tek ayrılan alanın sahibini takip et.
Brown · 4.1 · Collections Use Boxes dahil

Örnek / sahiplik a → b

fn main() {
    let a = Box::new([2, 4, 6]); // L1
    {
        let b = a; // L2
        println!("{}", b[0]);
    } // L3: b is dropped
}

Box değeri ile içindeki veriyi ayır

a, heap’teki [2, 4, 6] dizisini sahiplenen bir Box değeridir. Şemadaki ok, pointer’ın işaret ettiği veriyi gösterir.

let b = a; bir move işlemidir. b sahipliği alır; a eski değerini artık okuyamaz. Dizi heap’te ikinci kez oluşturulmaz.

canlı heap verisi / aktif sahipmoved / okunamazfonksiyon frame’i

H1 aynı ayrılan alanın kimliğidir; gerçek bir adres değildir. moved, “değer sıfırlandı” veya “null oldu” demek değildir.

Oluştur → taşı → bırak

Bu üç kare aynı programın farklı anlarıdır.

Derlenmez / E0382

let a = Box::new([2, 4, 6]);
let b = a;
println!("{}", a[0]); // ERROR: moved

H1 hâlâ b tarafından sahiplenilse de a üzerinden okuma reddedilir.

Bellek neden yalnızca bir kez bırakılır?

Normal kapsam çıkışında mevcut sahibin değeri bırakılır. Böylece aynı alanın iki kez serbest bırakılması ve bırakılmış veriye erişim engellenir.

drop(b) de Box’ın sahipliğini alıp erken bırakabilir. Move, kaynak yönetimini aktarır; heap verisini taşıması veya her zaman sıfır byte kopyalaması gerekmez.

KİŞİSEL RUST NOTLARI / 05 · OWNERSHIP 3/3

Rust / String’in yolculuğu

Çağrı, büyüme ve dönüşte aynı veriyi izle.
Brown · 4.1 · Collections Use Boxes dahil

Örnek / first → name → full

fn add_suffix(mut name: String) -> String {
    // L2: on entry, before push_str
    name.push_str(" Jr."); // L3
    name
}
fn main() {
    let first = String::from("Ada"); // L1
    let full = add_suffix(first); // L4
    println!("{full}");
}

String’in üç bilgisi

ptr
UTF-8 tamponunu gösteren pointer.
len
Kullanılan byte sayısı: “Ada” için 3, “Ada Jr.” için 7.
capacity
Tamponun byte kapasitesi; len değerinden küçük olamaz.

Şemalarda C ilk kapasite, C′ ekleme sonrası kapasitedir. Heap’te yalnızca kullanılan byte’lar çizilir. Alanların fiziksel sırası gösterilmez. L2 fonksiyona giriş anıdır.

“Collections Use Boxes”: String ve Vec heap alanını sahiplenir; doğrudan bir Box<T> alanı kullanmaları gerekmez.

Kapasite yeterliyse / C ≥ 7

Yeniden ayırma yapılmaz.
P′ = P, C′ = C.
Yalnızca kullanılan uzunluk 7 olur.

Kapasite yetmezse / C < 7

Tampon büyütülür; C′ ≥ 7.
Adres değişebilir, aynı da kalabilir. Belirli bir büyüme miktarı garanti edilmez.

Dönüş, veriyi bırakmaz

L4’te fonksiyon frame’i kalktı; döndürülen String’in sahibi full oldu. Sonrasında normal kapsam çıkışında full bu tamponu bırakır.

first, L2’den itibaren moved durumundadır; gri satır okunabilir bir eski pointer göstermez. full, ancak dönüş tamamlanınca başlatılır. Diyagramda boşluk ␠ ile gösterilir.

KİŞİSEL RUST NOTLARI / 06 · BORROWING 1/10

Rust / Sahipliği vermeden kullan

Bir değerin sahibi ile onu ödünç alanı ayır.
Brown · 4.2 · References & Borrowing

Bir fonksiyona yalnızca okuma erişimi ver

fn count_bytes(text: &String) -> usize {
    text.len() // L2
}
fn main() {
    let name = String::from("Ada"); // L1
    let size = count_bytes(&name); // L3
    println!("{name}: {size}");
}

Referans = sahip olmayan pointer

&name, name için bir referans oluşturur. Parametrenin tipi &String olur. String’in sahipliği taşınmaz.

fn consume(text: String) değerle alır ve sahipliği devralır. Buradaki count_bytes(text: &String) yalnızca ödünç alır.

Referansın işi bitince işaret ettiği veri bırakılmaz. Normal kapsam çıkışında String’i bırakacak olan hâlâ name’dir.

sahiplikshared referansmutable referans
Kendini yoklaFonksiyonun sonunda neden “Ada” silinmedi?Çünkü text referansı String’in sahibi değildi. Fonksiyon yalnızca sayıyı döndürdü.

L1 ve L3 işaretli satırın sonrası; L2 fonksiyonun içi. Bu sayfada kitaptaki tipe bağlı kalmak için &String kullanılıyor. Stack çizimi kavramsaldır; fiziksel yerleşim veya register kullanımı garantisi değildir.

KİŞİSEL RUST NOTLARI / 07 · BORROWING 2/10

Rust / Pointer yolunu takip et

Her * bir katman ilerler; & bir referans üretir.
Brown · 4.2 · References & Borrowing

Aynı sayıya iki farklı yol

let x = Box::new(7);
let r1: &Box<i32> = &x;
let r2: &i32 = &*x;
let a: i32 = **r1;
let b: i32 = *r2;
println!("{a} {b}"); // 7 7

İfade ile tipi birlikte oku

&x: x’in bulunduğu yere referans oluştur.

*r: r’nin işaret ettiği yeri belirt. Bu ifade tek başına “kopyala” emri değildir; nasıl kullanıldığı önemlidir.

Bu örnekte sonuç i32 olduğu için değeri okumak kopyalar. Her tip Copy değildir.

İfadeTür / ulaşılan yer7’ye ulaşmak için
r1&Box<i32> → x’in bulunduğu yer**r1
*r1Box<i32> türündeki yer; burada move edilmiyorBir * daha
r2&i32 → doğrudan heap sayısı*r2

Metot çağrılarında örtük adımlar

x.abs(), bu örnekte i32::abs(*x) ile aynı sonucu verir. Metot alıcısına otomatik borrow/dereference uygulanabilir; her ifadede otomatik dönüşüm var diye düşünme.

Kendini yoklar1 ile r2 neden aynı türde değil?Biri Box’a, diğeri Box’ın içindeki i32’ye referans verir.

KİŞİSEL RUST NOTLARI / 08 · BORROWING 3/10

Rust / Kuralların bellek nedeni

Aynı veriye erişim yolları birbiriyle çatışabilir.
Brown · 4.2 · References & Borrowing

Aliasing: aynı veriye birden fazla erişim yolu olması. item bir elemanı gösterirken values üzerinden tamponu değiştirmek bu referansı geçersiz kılabilir.

Derlenmez · item ileride kullanılacak

let mut values = vec![10, 20, 30];
let item = &values[2];
values.push(40); // ERROR: E0502
println!("{item}");

Derlenir · önce son kullanımı tamamla

let mut values = vec![10, 20, 30];
let item = &values[2];
println!("{item}"); // Last use
values.push(40);
println!("{values:?}");

Kapasiteyi büyütmek bu borrow hatasını çözmez

Her push yeniden ayırma yapmaz. Yine de push, &mut self ister. Sonradan kullanılacak eleman referansı varken, yeterli kapasite de olsa bu çağrı reddedilir.

İki ayrı soru sor

Derleyici neden reddetti? Shared borrow ile mutable erişim çakışıyor.

Hangi riski önlüyor? Örneğin tampon değişirken eski eleman adresinin geçersizleşmesini.

KİŞİSEL RUST NOTLARI / 09 · BORROWING 4/10

Rust / Shared borrow ve izinler

Aynı veriyi okumak
Referans ile hedefini ayrı düşün
Brown · 4.2 · References & Borrowing

&T, verinin sahipliğini almadan shared erişim sağlar. Borrow sürerken hedef okunabilir; hedefi değiştiren veya taşıyan erişimler kısıtlanır.

Önce oku, sonra Vec’i değiştir

let mut v = vec![10, 20, 30];   // 1
let item = &v[1];               // 2
println!("{}", *item);          // 3: last use of item
v.push(40);                     // 4
println!("{:?}", v);            // 5

Çıktı: 20, sonra [10, 20, 30, 40]. 3. satırdan sonra item yeniden kullanılmadığı için 4. satırdaki push geçerlidir.

Her satır tamamlandıktan sonraki durum

Satır SONRASIvitem*item
1 · değer hazırRWOhenüz yokhenüz yok
2 · shared borrowR––R–OR––
3 · son kullanımRWOartık kullanılmıyorartık kullanılmıyor
4 · push bittiRWOartık kullanılmıyorartık kullanılmıyor

R okuma · W değiştirme · O move/drop. Bunlar çalışma zamanı bayrakları değil, derleme zamanı erişimlerini anlatan bir modeldir.

Place: bir bellek konumunu belirten ifade. v, v[1] ve *item buna örnektir. Her place yazılabilir değildir.

Sırayı değiştirirsen: E0502

let mut v = vec![10, 20, 30];
let item = &v[1];
v.push(40); // ERROR: item is used later
println!("{}", *item);

item daha sonra okunacağı için borrow sürer. push mutable erişim ister. Önceden kapasite ayırmak da bu borrow çatışmasını çözmez.

Kendini yokla3. satırda izinlerin dönmesi, item değişkeninin silinmesi veya verinin drop edilmesi midir?Hayır. Burada yalnızca borrow’a artık ihtiyaç yok. Daha sonraya bir item kullanımı eklemek borrow’u uzatır; R izni de her değeri Copy yapmaz.

KİŞİSEL RUST NOTLARI / 10 · BORROWING 5/10

Rust / Mutable borrow: kim yazabilir?

Binding ve hedefin mutability’si
Aynı şey değildir
Brown · 4.2 · References & Borrowing

&mut T, ödünç alınan veriye tekil erişim sağlar. Bu örnekte borrow sürerken erişim item üzerinden yapılır; v doğrudan kullanılamaz.

Değer, referans üzerinden değişir

let mut v = vec![10, 20, 30];   // 1
let item = &mut v[1];           // 2
*item += 5;                     // 3
println!("{}", *item);          // 4: last use of item
println!("{:?}", v);            // 5

Çıktı: 25, sonra [10, 25, 30]. let item binding’i immutable olsa da *item değiştirilebilir.

Her satır tamamlandıktan sonraki durum

Satır SONRASIvitem*item
1 · değer hazırRWOhenüz yokhenüz yok
2 · mutable borrow–––R–ORW–
3 · hedef değişti–––R–ORW–
4 · son kullanımRWOartık kullanılmıyorartık kullanılmıyor

2–3. satırdan sonra v yerinde kalır; sahiplik item’a geçmez. Kısıtlanan, v üzerinden doğrudan erişimdir.

İki farklı yerdeki mut, iki farklı izin

Bildirimr = …*r = …
let r = &x;HayırHayır
let mut r = &x;EvetHayır
let r = &mut x;HayırEvet
let mut r = &mut x;EvetEvet

Her satır ayrı bir senaryo: x uygun biçimde mutable, yeni hedefin tipi/ömrü uygun ve başka bir borrow kısıtı yok varsayılır. r = … referansı; *r = … gösterilen veriyi değiştirir.

let mut r = &x: değişebilen referans binding’i

r başka bir shared referansa atanabilir. Ancak &T üzerinden hedefe doğrudan yazılamaz: mut r, hedefi mutable yapmaz.

let r = &mut x: değişebilen hedef

r başka referansa atanamaz; *r değiştirilebilir. Mutable referans ownership vermez: *r içindeki String gibi bir değeri yalnızca dereference ederek dışarı taşıyamazsın.

Kendini yokla“Tek mutable referans” programın tamamında yalnızca bir &mut bulunabilir demek mi?Hayır. Kural, aynı veya örtüşen veriye erişimle ilgilidir. Ayrıca son kullanım sonrası ödünç alan referans üzerinden erişim artık gerekmediğinde sahibin izinleri geri dönebilir.

KİŞİSEL RUST NOTLARI / 11 · BORROWING 6/10

Rust / Reborrow: geçici shared erişim

&*unique nasıl okunur?
Hedef aynı, izinler geçici değişir
Brown · 4.2 · References & Borrowing

&*unique: önce *unique ile hedefin yerini belirle, sonra & ile o yeri shared ödünç al. unique’un tipi hâlâ &mut i32.

RW → R → RW: yazı izni geri gelir

let mut score = 10;                // 1
let unique = &mut score;           // 2
*unique += 1;                      // 3
let shared = &*unique;             // 4
println!("{} {}", *unique, *shared); // 5
*unique += 1;                      // 6
println!("{}", *unique);           // 7: last unique use
println!("{}", score);             // 8

5. satırda iki referans da okuyabilir. 6. satırdaki yazma, shared’ın son kullanımından sonradır. Çıktı: 11 11, 12, 12.

Referansların gösterdiği yerlerin izinleri

Satır SONRASI*unique*shared
3 · shared henüz yokRW–henüz yok
4 · shared kullanılacakR––R––
5 · son shared kullanımıRW–artık kullanılmıyor
6 · unique ile yazıldıRW–artık kullanılmıyor

score’a doğrudan erişim, unique’un 7. satırdaki son kullanımından sonra geri gelir. Tablo unique binding’ini değil, *unique hedefini gösteriyor.

Yazmayı öne alırsan: E0506

let mut score = 10;
let unique = &mut score;
let shared = &*unique;
*unique += 1; // ERROR: shared is used later
println!("{}", *shared);

shared daha sonra okunacağı için *unique yazı iznini henüz geri alamaz. Bu program derlenmez.

Kendini yoklashared varken unique üzerinden okumak da yasak mı?Hayır: bu shared reborrow sırasında *unique için R kalır, W geçici kısıtlanır. Son kullanımın bitmesi drop veya değerin yok olması anlamına gelmez.

KİŞİSEL RUST NOTLARI / 12 · BORROWING 7/10

Rust / Lifetime: son kullanım

Borrow’un bitişi ile kapsam sonunu ayır.
Brown · 4.2 · References & Borrowing

Çalışır / aynı blok içinde önce oku, sonra değiştir

{
    let mut s = String::from("hi"); // L1
    let r = &s;                    // L2
    println!("{r}");                // L3
    s.push('!');                    // L4
    println!("{s}");                // L5
}                                  // L6

İki ayrı bitiş anı

r adının kapsamı } noktasına kadar sürer. Bu programda borrow, L3’teki son kullanımın ardından artık gerekmez; s üzerindeki W/O izinleri geri gelir.

L4’te değişiklik yapılabilir. s ise son okunduğu L5’te değil, normal kapsam çıkışında L6’da bırakılır.

Yeni bir son kullanım eklersen / E0502

let mut s = String::from("hi");
let r = &s;
println!("{r}"); // earlier use
s.push('!');    // ERROR: r is still needed
println!("{r}"); // last use

Derleyici ilerideki kullanımı da hesaba katar

İkinci println! eklendiğinde ilk yazdırma artık r’nin son kullanımı değildir. Borrow, aradaki s.push('!') satırını da kapsar.

Bu satırın istediği W izni yoktur. İkinci okumayı da değişiklikten önce yaparsan örnek tekrar geçerli olur.

Kendini yoklaÇalışan örnekte L3 bittiğinde s’nin heap tamponu serbest bırakılır mı?Hayır. Borrow artık gerekmiyor; String’in sahibi hâlâ s. Normal drop noktası L6.

KİŞİSEL RUST NOTLARI / 13 · BORROWING 8/10

Rust / Lifetime dallara ayrılabilir

Her kontrol akışı yolunda son kullanımı bul.
Brown · 4.2 · References & Borrowing

İki çağrı / iki farklı yol

Önkoşul: v boş değil; v[0] ilk karaktere erişir.

fn capitalize(v: &mut Vec<char>) {
    let c = &v[0]; // L1
    if c.is_ascii_lowercase() { // L2
        let upper = c.to_ascii_uppercase(); // L3
        v[0] = upper; // L4
    } else {
        println!("Unchanged: {v:?}"); // L5
    }
}
fn main() {
    let mut lower = vec!['h', 'i'];
    let mut upper = vec!['H', 'i'];
    capitalize(&mut lower);
    capitalize(&mut upper);
    println!("{lower:?} / {upper:?}");
}

then / L3’ü bekle

Koşuldan sonra c bir kez daha okunur. Bu yüzden *v üzerindeki W, c.to_ascii_uppercase() tamamlanana kadar geri gelmez. upper, elde edilen ayrı bir char değeridir.

else / dal girişinde hazır

Bu yolda c’nin son kullanımı koşuldadır. Else’e girildiğinde borrow artık gerekmez. *v W iznini geri kazanır; örnekteki yazdırma yalnızca okur.

v ile *v aynı yer değildir

v, &mut Vec<char> türündeki referans parametresidir. *v, erişilen Vec’tir. Geri gelen W, *v üzerindedir; Vec’in sahibi main içindedir.

Kendini yoklaElse dalına println!("{c}") eklense W yine dal girişinde geri gelir mi?Hayır. O yolda c yeniden kullanılacağı için borrow bu yeni son kullanıma kadar gerekli olur.

6 kısa soru · Önce tahmin, sonra gerekçe

Önce tahmin et, sonra nedenini söyle. İzin sorularında referans değişkeni ile işaret ettiği yeri ayrı düşün. Yanıtlar sonraki sayfada.

01 · Yıldızları takip et

let n = Box::new(12);
let r = &n;
let value = **r + 1;
println!("{value}");

Çıktı ne olur? r ve **r hangi türdedir? Burada kutunun sahipliği taşınır mı?

02 · Çağrıdan sonra sahibi

fn size(s: &String) -> usize { s.len() }
fn main() {
    let name = String::from("Ada");
    let count = size(&name);
    println!("{name}: {count}");
}

Son satır derlenir mi? Fonksiyon bitince name neden silinir veya silinmez?

03 · Değişen referans mı, sayı mı?

let a = 4;
let b = 9;
let mut r = &a;
r = &b;
*r += 1;

Hangi işlem reddedilir? let mut r hangi yeri değiştirmeye izin verir? Sayıyı artırmak için ne gerekir?

04 · İzinlerin zamanı

let mut v = vec![3, 6];
let r = &mut v[0]; // A
*r += 2;
println!("{r}");   // B
v.push(9);
println!("{v:?}");

A satırından hemen sonra v ile *r hangi R/W/O izinlerine sahiptir? B bittikten sonra push yapılabilir mi?

05 · Ödüncün içinden ödünç

let mut n = 10;
let r = &mut n;
let s = &*r;
*r += 1;
println!("{s}");

Bu sıra derlenir mi? Hangi yerin hangi izni eksik? Yeni değişken eklemeden iki işlemden hangisini öne alırsın?

06 · İki dal, iki son kullanım

let mut v = vec![7];

if *r > 5 { println!("{r}"); }
else { v.push(0); }
v.push(9);

Program derlenir mi? Her dalda r için son kullanım neresi? else içindeki ve sondaki push neden geçerli veya geçersiz?

Rust / Yanıtlar ve nedenleri

İşlem → gereken izin → son kullanım
Brown · 4.2 · References & Borrowing

Sonucu bildiğin kadar gerekçeyi de kontrol et: Hangi yer? · Hangi izin? · Ödünç ne zaman bitiyor?

01 · Okumak, sahipliği almak değildir

Çıktı: 13. r: &Box<i32>; **r: i32. İlk yıldız kutuya, ikincisi içindeki sayıya erişir.

İşlem / izin: sayıyı okumak R ister; i32 kopyalanır, kutu taşınmaz. r son kez **r + 1 içinde kullanılır.

Engel yok: ortak referans okuma sağlar; burada kutudan sahiplik almaya veya veriyi değiştirmeye çalışmıyoruz.

02 · Referans sahiplik taşımaz

Derlenir; çıktı: Ada: 3. s, name verisinin sahibi değildir. Fonksiyonun bitmesi bu metni silmez.

İşlem / izin: uzunluğu okumak R ister. Çağrı yalnızca bir sayı döndürür; ödünç, bu çağrının ardından sona erer.

Engel yok: name sahipliği main içinde kalır; son satır metni okuyabilir. Sebep, metnin sonraki satırda kullanılıyor olması değildir.

03 · İki ayrı mutability kararı

*r += 1 reddedilir (E0594). r = &b geçerlidir: let mut r, referans değişkenine W verir; *r için W vermez.

İşlem / izin: artırma R ve W ister; &i32 üzerinden yalnızca okunabilir. Son kullanıma gelmek bu referansı mutable yapmaz.

Çözüm: sayıyı let mut b = 9 ile tanımla, let r = &mut b üzerinden *r += 1 yap. Referans bağının mut olması gerekmez.

04 · Geçici kısıtlama, ardından geri dönüş

A sonrası: v → izin yok; *r → R ve W. Mutable borrow sürerken vektörün asıl yerinden erişilemez; sahiplik yine v’dedir.

İşlem / izin: *r += 2 R/W ister. r son kez B’de okunur; ardından v R/W/O izinlerini geri alır.

push geçerlidir: gereken R/W artık vardır. Çıktı önce 5, sonra [5, 6, 9]. B’den sonra r tekrar kullanılsaydı bu sıra engellenirdi.

05 · Yazma izni yeniden ödünçte bekler

Derlenmez (E0506). &*r ortak bir yeniden ödünç oluşturur; s kullanılacakken *r okunabilir ama yazılamaz.

İşlem / izin: *r += 1 R/W ister; W eksiktir. s için son kullanım, println!("{s}") satırıdır.

Çözüm: bu println! satırını artırmadan önceye taşı. Son kullanım bitince *r W iznini geri alır; önce 10 yazılır, sonra sayı 11 olur.

06 · Son kullanım yürütme yoluna bağlıdır

Derlenir; iki push da geçerlidir. then yolunda r son kez println! içinde; else yolunda ise koşulda kullanılır.

İşlem / izin: koşul ve yazdırma R, push R/W ister. else girişinde ve if sonrasında v W iznini geri almıştır.

Engel yok: izinleri geri getiren yeni süslü parantezler değil, o yoldaki son kullanımdır. Bu girdiyle çıktı 7, ardından [7, 9] olur.
